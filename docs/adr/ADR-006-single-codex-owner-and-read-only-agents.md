# ADR-006: One Writable Codex Owner; Graphify and Hermes Stay Read-Only

- Status: accepted; approved by user on 2026-07-29
- Date: 2026-07-29
- Decision owner: user
- Related: SPEC-002, ADR-002, ADR-004

## Context

OpenClaw can manage Codex app-server through its official harness. Hermes can
also optionally hand turns to Codex app-server. A Rust LATTICE core can
independently speak the same app-server protocol.

Using more than one of those paths to resume or write the same native thread
would split process ownership, approval routing, cancellation, evidence
sequencing, and writer authority. It would violate One Writer even if only one
model response appears visible.

## Recommended Decision

- The Rust LATTICE core directly owns the single writable Codex app-server
  child process and native thread used for an approved implementation task.
- OpenClaw remains the only normal human gateway but calls LATTICE through a
  thin local IPC plugin. It does not own the writable Codex harness/thread.
- Hermes does not use a writable Codex runtime inside the LATTICE research
  lane.
- Graphify and Hermes receive immutable read-only product inputs and cannot
  obtain a product worktree lease. Their required output goes only to separate
  LATTICE-owned candidate/artifact directories.
- Reviewers use snapshots/diffs/evidence and never reuse the Implementer's
  mutation capability.

## Codex Adapter Contract

- Use stdio JSONL first; experimental remote transports are outside the initial
  scope.
- Verify all three independently: exact executable identity/version/digest, a
  protocol schema generated by that exact binary and bound by hash, and
  explicit feature probes for every required method/notification. Codex is not
  assumed to provide complete automatic capability negotiation.
- Use a dedicated LATTICE-owned `CODEX_HOME` and verify the
  `initialize.codexHome` result. The user's normal Codex home is not used
  without explicit approval.
- Bind one app-server process, one LATTICE task attempt, one native thread
  policy, one worktree, and one lease.
- Normalize streamed items, permission requests, completion, token usage,
  errors, overload, and interrupts into LATTICE events. Monetary cost is
  derived only from a separately pinned pricing/account model and otherwise
  remains `unknown`; it is not assumed to be app-server-native evidence.
- Evaluate permission requests through LATTICE policy.
- Treat worktree confinement as a LATTICE invariant, not an app-server
  guarantee: use an RPC allowlist, fixed permission profile, independently
  verified OS/process containment, and exact post-run Git/path Scope Check.
- On stop, prevent new effects, issue interruption, wait a bounded interval,
  terminate if required, reconcile outcome, and revoke the lease before review.
- Unknown schema/version, second owner, missing completion, or ambiguous
  side-effect outcome fails closed.

## Graphify Adapter Contract

- Begin with local code-only extraction against an immutable snapshot.
- Do not call `graphify install`, install hooks/skills, or write configuration
  into the product repository.
- Mount/expose source read-only and direct all output to a separate
  LATTICE-owned artifact staging directory. If the pinned version cannot
  separate source and output, preflight fails closed.
- Code-only mode forbids semantic backends, live PostgreSQL introspection, and
  optional external integrations.
- Record snapshot/tool/adapter versions, source commit/tree, capability hash,
  artifact hash, and build result.
- Preserve `EXTRACTED`, `INFERRED`, and ambiguous provenance.
- Treat artifacts as derived, rebuildable evidence, not control truth.
  Byte-for-byte reproducibility for pinned input/tool/config is a LATTICE
  acceptance test, not an upstream guarantee.

## Hermes Adapter Contract

- Use a dedicated `HERMES_HOME`/profile for state separation plus independently
  enforced whole-process OS containment, a read-only product mount, a separate
  candidate-output directory, and no Git/database credentials. A profile alone
  is not a security boundary.
- Prefer the documented programmatic API/JSON-RPC surface over terminal text
  scraping.
- Request a bounded research/reflection run with a deadline and capability set.
  Hermes may return arbitrary output; LATTICE accepts only a versioned,
  schema-valid candidate envelope with required provenance, and rejects or
  quarantines anything else.
- Store accepted envelopes as untrusted candidates; Hermes-internal memory,
  skills, guard-agent settings, and approval toggles are defense in depth and
  never become LATTICE authority.
- No product writer lease, general DB credential, release promotion, or
  writable Codex runtime is exposed.

## Review Runtime Contract

- Review runs through a dedicated read-only `review-runtime` port.
- A Codex reviewer, if selected, uses a separate process/thread/profile without
  the Implementer's writer lease or mutation capabilities.
- The reviewer set, evidence inputs, and acceptance hash are frozen in the Task
  Packet before review.
- The same model/runtime that produced a change cannot be its sole acceptance
  authority. Protected or high-risk changes retain responsible-human approval.
- A memory `PREFERENCE` may become accepted only from authenticated user
  evidence. Model-derived preferences remain `INFERENCE/CANDIDATE`.

## Alternative Considered

Let OpenClaw's official Codex harness own implementation while Rust observes.
This reduces custom process integration, but splits the authoritative writer
lease/effect outbox from the process that owns app-server lifecycle, approval
relay, and cancellation. It is not recommended for the first enforceable
version.

## Consequences

- One component can enforce worktree, lease, policy, cancellation, and evidence
  sequencing around the code writer.
- OpenClaw still provides the user experience but not direct Codex ownership.
- LATTICE must maintain a versioned Codex app-server client and capability
  preflight.
- The current official Codex manual labels app-server experimental; LATTICE
  must keep the protocol behind a replaceable adapter and cannot promise a
  stable compatibility floor before exact-version evidence.
- Hermes and Graphify are useful without becoming a second planner/writer/truth.
