## Objective

Produce the first runnable segment of the delivery-first product path. The
existing `apps/lattice-runtime` package becomes the canonical `latticed`
composition root over a pure Rust orchestrator and typed delivery ports. It
records intent in real PostgreSQL, supervises the official Codex app-server to
modify an isolated Git repository, runs the fixed verification command,
creates a local commit, records the terminal result, and can replay status from
PostgreSQL. The existing `lattice-runtime` command remains a compatibility
wrapper over the identical composition.

## Acceptance Criteria

- [x] Contracts 1.10 and Ports 1.6 expose typed delivery
  request/evidence/status plus delivery-ledger, bounded workspace/Git, and
  fixed-test traits with no concrete driver, command line, SQL, credential, or
  MCP type.
- [x] Orchestrator 2.1 has no concrete adapter or transport dependency and can
  only order durable intent -> bounded workspace preparation -> Codex ->
  changed-path inspection -> fixed test -> Git commit -> durable
  outcome/receipt. The first failed or uncertain stage prevents every later
  effect.
- [x] The existing `apps/lattice-runtime` package implements the sole normal
  `latticed` composition root and exposes exactly two MCP stdio tools suitable
  for Codex App registration: `lattice_delivery_run` and
  `lattice_delivery_status`. Both have zero-parameter closed object schemas;
  shell, SQL, path, credential, provider, arbitrary-task, and extra-property
  inputs are rejected before dispatch. This does not expand `lattice-cli` or
  replace OpenClaw as the normal gateway.
- [x] The `lattice-runtime` compatibility wrapper invokes the identical
  `latticed` composition, adapter set, PostgreSQL truth, and status projection;
  it cannot establish a second orchestrator or gateway.
- [x] The Codex adapter captures exact executable path, version, SHA-256, and a
  schema digest generated by that same binary before starting a task.
- [x] The adapter owns a real `codex app-server --listen stdio://` process,
  initializes it, starts one bounded thread/turn, observes an unambiguous
  terminal result, and can interrupt or fail closed.
- [x] The acceptance path uses a newly created isolated Git repository, permits
  only its declared file, runs a fixed local test, rejects foreign changes, and
  creates a real local commit only after verification passes.
- [x] Intent, component identity, changed-path/test/commit evidence, and the
  terminal outcome are stored in a real marker-owned PostgreSQL instance and
  reloaded by a separate status invocation.
- [x] Process loss, timeout, malformed protocol, failed test, scope drift, Git
  ambiguity, or database ambiguity never reports success; uncertain effects
  become reconciliation-required.
- [ ] A repeatable PowerShell acceptance command proves the full TASK-032 path
  from a clean checkout and emits machine-readable evidence.

## Non-Goals

- Claim that MVP-1 is complete before real OpenClaw, Graphify, Hermes, and
  Codebase Memory nodes join the same executable path.
- Turn the bounded Codex App MCP entry into a general task, shell, SQL, path,
  credential, provider, approval, stop, Guardian, release, or deployment
  gateway.
- Mutate an existing user product repository in this first acceptance run.
- Push, merge the primary branch, publish, deploy, pay, expose a public service,
  or activate self-upgrade authority.
- Finish paused TASK-022 governance or add unrelated documentation.

## Module And Constitution Constraints

- `codex-adapter` 1.1 owns only Codex process/protocol identity and typed
  evidence; it cannot call Git, tests, PostgreSQL, or another adapter.
- `lattice-contracts` 1.10 owns representation only and performs no I/O or
  authority decision.
- `lattice-ports` 1.6 owns trait signatures only and depends only on Contracts;
  `DeliveryCodexPort` is the sole production delivery writer boundary while
  generic `CodexPort` remains frozen outside this composition.
- `orchestrator-runtime` 2.1 owns pure injected-port effect ordering and has no
  concrete Codex, PostgreSQL, workspace, test, Git, or MCP dependency.
- `latticed` 1.0 alone selects concrete adapters and exposes bounded MCP stdio;
  the compatibility command delegates to that same composition.
- `postgres-store` 1.4 remains the only durable task/result truth used here.
