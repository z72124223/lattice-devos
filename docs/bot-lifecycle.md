# Bot 生命週期與工程交接

更新：2026-09-07。狀態：**設計目標；本次只更新說明，沒有啟用自動換班。**

目標是在上下文壓力或品質下降前預防性換班，讓新窗口從可核對的工程狀態接續。
角色與工作 ID 長期保留，Codex 窗口作為可替換的執行者。換窗口本身不是品質
通過證明；每次換班都必須驗證工程、未完成事項及責任歸屬。

## 分工與目前邊界

| 部分 | 責任 | 本設計的實裝邊界 |
|---|---|---|
| Codex 原生能力 | 推理、窗口與回合、上下文及壓縮、工具與核准、建立／續接窗口、傳訊、既有排程與封存 | 依實際主機與工具能力使用；LATTICE 不另造代理迴圈、上下文儲存或排程器 |
| LATTICE／PostgreSQL | 擬保存角色、窗口世代、唯一有效負責者、換班政策、工作清單、交接版本與驗收證據 | 需補齊並驗證完整的角色生命週期；不可把既有任務租約／工頭恢復等同所有 Bot 自動換班 |
| 全域及專案指示 | 要求新窗口接入、讀取正式狀態與規則；專案保留工程與授權邊界 | 指示文字不是硬性寫入攔截，既有窗口須明確載入新版並保存讀回結果 |
| 工程資料與 GitHub | 保存程式碼版本、文件、PR 與檢查證據 | GitHub 提交不包含所有本機未提交內容、資料庫、執行中的服務或認證狀態 |

既有工作身分、收據重播與 Writer 輪替是可沿用的基礎，但本次文件未新增它們的
功能或重新驗證全部路徑。完整的逐窗口計量、預防性觸發、交接驗收、角色切換、
排程改綁及舊窗口阻擋尚須端到端證據；不能由單一狀態查詢或文件推定已完成。

## 新舊 Bot 如何接入

- **新窗口**：在適用的 Codex 全域 `AGENTS.md` 放置穩定接入規則；啟動後先確認
  LATTICE 可用，再讀回專案、工作、角色、世代及目前負責者。尚未綁定就標示
  未納管，不自稱已接班或自行建立第二個修改者。
- **既有窗口**：明確通知載入新版規則，保存規則版本、窗口／主機身分及實際
  讀回結果。更新磁碟文件不等於正在執行的窗口已載入。
- **其他主機與雲端**：分別登記來源與驗證工具、資料存取及排程；一台電腦的
  全域設定不能代表所有環境已生效。短期子代理沿用父工作的有界責任，不自行
  接管常設角色；未納管對話不能算入生命週期覆蓋率。
- **狀態來源失聯**：保留最近可驗證狀態，停止新的角色接管與不確定重派；
  對進行中的操作先觀察、收斂和保存，不以猜測切換負責者。

## 預防性門檻與持續保存

門檻必須在啟用前設定並記錄政策版本、度量來源、觀察時間與適用範圍。可量測的
上下文使用量、實質工作回合與有界階段可供校準；帳號總用量不能代替逐窗口
上下文。缺少度量時標示未知，不能虛構比例或宣稱已精確自動輪替。

到達門檻應提前停止接新工作，預留保存與交接空間，將當前操作收斂到可恢復的
檢查點。門檻不能在資料庫操作、寫檔、提交或外部動作途中直接殺掉執行者；
遇到不確定操作結果，必須先查證，不能由新窗口盲目重做。

每個可驗收工作階段都要保存必要進度；文件大小應與工作相稱。交接資料平時
就要存在，不能直到換班時才靠舊窗口的記憶整理。

## 交接與接管順序

1. **保存並停止接新工作**：舊窗口保存精確版本的交接資料及在途操作；切換期間
   的新訊息仍须有記錄及責任歸屬，避免只送往即將封存的窗口。
2. **新窗口唯讀核驗**：讀原始需求、工程狀態與證據，列出相同的未完成工作及
   下一步，執行風險相稱的基本檢查；不得只回覆「已了解」。
3. **核對交接期間的增量**：驗收期間若出現新回報、使用者決定或檔案變更，先
   補進交接版本並重新核對受影響項目，不提交已過期的交接。
4. **切換唯一負責者**：目標是在 LATTICE 以預期舊世代與交接版本檢查，原子地
   將有效負責者切至新世代。舊窗口在切換後不得接新案或繼續產品寫入。
5. **更新 Codex 映射並讀回**：由已授權的原生操作更新收件位置與既有排程，保留
   頻率及通知偏好。LATTICE 與 Codex 不假裝是同一個原子交易；中途失敗要記錄
   已完成步驟、查證外部結果並恢復，避免重建排程或重複派工。
6. **驗證後封存**：確認沒有未歸屬工作、未收回報、在途操作或待處理輸入，且
   新窗口已通過驗收，才封存舊窗口。保留舊歷史、工程資料與交接證據。

切換前失敗，保留原有效負責者。切換後部分步驟失敗，先讀正式世代及原生結果，
只由已確認的有效負責者恢復；不能讓兩代同時繼續寫入，也不能只改顯示名稱
冒充回復成功。每次切換須有唯一識別，重試應讀回同一結果。

## 「完整交接」必須核對的內容

| 核對項目 | 驗收要求 |
|---|---|
| 工作責任 | 工作 ID、未完成清單、依賴、阻礙、待決定事項與在途訊息全部對得上；有意變更需有來源 |
| 需求與授權 | 原始需求、已確認決策及理由、不可擴張的操作權限、下一步均可追溯 |
| 工程版本 | 倉庫／工作目錄、Git 提交、分支、未提交與未追蹤變更及必要產物都能定位；不為換班而清理或覆寫 |
| 執行環境 | 必要工具、資料庫及服務狀態、可恢復步驟與未決操作結果可核對；不把程序或登入狀態當作已自動移轉 |
| 品質證據 | 分清已執行檢查、來源自報、未執行與失敗；新窗口能重跑必要的基本驗證 |
| 接入與收件 | 唯一有效世代、規則版本、原排程與待收回報均已讀回，其他 Bot 從正式映射取得收件者 |

認證秘密及私人業務原文不寫入 GitHub，也不複製到交接摘要；只保留獲授權的
存取方式或必要的人類認證交接。驗收失敗須保留具體差異，不能標記成功。

## 執行約束與啟用驗收

硬性保護必須在**受管理的派工與寫入入口**檢查有效負責者及世代，並拒絕過期
請求。若 Codex 能繞過該入口直接寫檔，這部分就不在 LATTICE 的攔截範圍內；
不能用 `AGENTS.md`、接入回執或定期巡檢聲稱已控制所有原生操作。

啟用前至少實測正常換班、交接缺項、驗收期間新增訊息、過期世代寫入、重複
切換請求、窗口／主機失聯，以及排程更新到一半中斷的恢復。驗收證據應同時
指出受保護入口和未覆盖範圍。成功標準是可核對、可恢復、不靜默遺漏、不雙寫；
不承諾任何模型或執行環境永遠不故障。
